# Fleeting · 随笔：需求与产品设计

> 初稿：2026-10-07。当前为需求与设计阶段，尚未实现。
> 「明确需求」来自用户描述；其余为设计建议，不代表用户已确认。

## 1. 产品定位

一个私人的、随手即写的文字空间。记录时不必组织语言，回顾时帮助自己看见生活和思考的脉络。

核心体验：**随手记 → 当天整理 → 长期洞察**。

不做复杂笔记管理系统，不要求标题、标签、文件夹，不用打卡、连续记录天数或评分制造负担。AI 是整理者与提问者，不是对用户下结论的评判者。

## 2. 已明确的需求

- 名称：英文 Fleeting，中文「随笔」。
- Web 前端，同时适配横版、纵版页面。
- 私人使用，需要登录、不需要注册；登录只输入密码，密码在服务端配置文件中配置。
- 界面非常简单，进入后即可输入文字；点击「完成」保存文字和时间，然后继续写。
- 按天存储、查看记录与整理结果。
- 提供「总结」按钮，手动整理当天文字。
- 日总结需通顺、有条理，不丢失内容细节，保留不必过细的时间线。
- 后续配置大模型 API 密钥。
- 可分析月度等更长时间段，以图文展示类别、主题和思考；希望有深入、多角度、有趣、有启发性的归纳。
- 常见内容：生活感悟、随时想法、亲子关系、亲情、心理学、产品开发、技术、创业、一人公司、如何用 AI。

## 3. 产品结构：三个入口

### 3.1「随笔」：默认首页

页面核心只有一个输入框和「完成」按钮。

- 顶部：Fleeting · 随笔，以及低干扰的「回看」「洞察」入口。
- 输入框提示：「此刻，想记下什么？」不限定内容。
- 不要求标题、标签、情绪或分类。
- 点击完成后，服务端确认保存成功才清空输入；输入焦点保留，方便继续写。
- 下方是今天的记录，展示时间和原文；建议最新记录靠近输入区。
- 「总结今天」放在今日记录标题旁，视觉层级低于完成按钮。
- 记录编辑、删除放在每条记录的次级菜单里；删除可撤销。
- 建议支持 Cmd/Ctrl + Enter 保存，普通 Enter 换行。
- 无内容时不允许提交；保存中防止重复点击，接口使用幂等标识避免重试生成重复记录。

可靠性优先：

- 保存失败不清空输入，明确显示未保存并允许重试。
- 建议提供本机草稿恢复；私人内容在本机保留需明确告知，退出登录时清除本机草稿与敏感缓存。
- 首版不承诺完整离线同步；网络中断时至少保护当前输入。
- 记录正文按纯文本安全渲染；AI Markdown 渲染需过滤不安全内容。

### 3.2「回看」：按天浏览

- 默认按日期分组的记录列表，支持选择日期；不强制使用占据大面积的月历。
- 选定日期后，可切换「原始记录 / 当日整理」。
- 无需先总结才可归档；原始记录保存时就属于相应日期。
- 整理结果有对应日期、生成时间、所用记录数量及来源引用。
- 当日新增、修改或删除记录后，原整理标记为「有更新，待重新整理」，不悄悄覆盖。
- 可整理过去某一天，不限于今天。
- 文字搜索、导出建议纳入首版或紧接首版补齐。

### 3.3「洞察」：一段时间的回顾

- 选择本周、本月、上月或自定义日期范围，手动生成。
- 首屏不做满屏仪表盘：展示一句阶段概括、2–4 个关键发现、一张主题图。
- 下面渐进展开思考演变、跨主题关联、未解问题与原文证据。
- 每次基于材料选择最有价值的分析维度，不硬凑固定的十项分析。
- 样本少时明确写「材料较少，仅能做初步归纳」，不强行作深度判断。

## 4. 页面与视觉建议

关键词：安静、留白、轻、以文字为主。温暖的浅色背景，深灰正文，一种克制的强调色，时间等元信息弱化但保持可读。

### 竖屏 / 手机

```text
Fleeting · 随笔             回看  洞察

┌──────────────────────────────┐
│ 此刻，想记下什么？            │
│                              │
│                       [完成] │
└──────────────────────────────┘

今天 · 10 月 7 日          总结今天

14:35
刚刚想到……

09:10
早上和孩子……
```

- 单列，输入区在上；整理结果作为独立页面或全屏视图，不塞进窄侧栏。
- 移动端输入字体不小于 16px，按钮有足够触摸区域；软键盘弹出时仍可操作完成按钮。
- 横屏手机或低高度窗口不强制两栏，以实际可用宽高决定布局。

### 横版 / 桌面

```text
Fleeting · 随笔                            随笔  回看  洞察

┌───────────────────────────┐  ┌─────────────────────┐
│ 此刻，想记下什么？         │  │ 今日整理            │
│                    [完成] │  │ 上午 · ……           │
├───────────────────────────┤  │ 下午 · ……           │
│ 今天的原始记录             │  │                     │
│ 14:35 ……                  │  │ 查看来源 / 重新整理 │
│ 09:10 ……                  │  │                     │
└───────────────────────────┘  └─────────────────────┘
```

- 默认仍以舒适宽度的写作主栏为中心；只有查看整理时才展开第二栏，避免空白面板。
- 长期报告在宽屏采用图文并排，窄屏上下排列；图表附文字说明，不只靠颜色传递信息。
- 首版不需要复杂后台页面，配置文件承担管理职责。

## 5. 当日总结：更准确地说是「保真整理」

### 5.1 与普通摘要的区别

不是把一天压成几句话，而是把零散表达整理成可重读的文字。**可减少口头重复，不能因为追求简洁而删去独立信息。**

保留：事件、人物、具体例子、数字、条件、情绪的自述、疑问、设想、结论及不确定性。互相矛盾的想法也保留，不替用户消除矛盾。

以第一人称为主，保留个人语气；不增添原文没有的事件、动机、感受或因果关系。当天整理不掺入 AI 建议，建议放在洞察区。

### 5.2 输出结构

- 日期与可选的简短标题。
- 按上午 / 下午 / 晚间，或合理的时间范围分段。
- 每个时段内部按主题组织成通顺段落；不必逐分钟罗列。
- 每段附可展开的原始记录引用。
- 简短的「今日线索」可以存在，但不能代替详细整理正文。

时间规则：默认时间线表示记录发生的时间，而非所述事件的时间。若下午写「昨天晚上发生了……」，保留这种区别，不把事件错写成下午发生。

### 5.3 保真流程

1. 取该日全部原文，按记录时间排序，为每条分配可引用 ID。
2. 从原文抽取信息点，标记事件、观点、例子、问题、限定条件及对应 ID。
3. 按粗时间段生成保真整理，维护段落到来源的映射。
4. 用原文与信息点核对整理结果，尝试补齐遗漏并删除无依据的增补。
5. 保存结果、来源版本及生成状态，允许随时对照原文。

AI 核对不能数学上保证绝无遗漏，因此「不丢细节」是质量目标，不对模型作绝对承诺。原文始终是可信依据；整理不替代、不覆盖原文。

长文本按时间片分块，再合并；合并时保留信息点及引用，不能仅对短摘要反复摘要。

## 6. 长期洞察：不止于分类统计

以下为候选能力。首版建议优先主题分布、思考演变、开放问题，其余逐步加入。

| 分析维度 | 关心的问题 | 建议呈现 | 约束 |
| --- | --- | --- | --- |
| 主题分布 | 这段时间写了什么？ | 多标签横向条形图 + 每类说明 | 分类可重叠，合计不必为 100%；频次不代表重要性 |
| 关注变化 | 哪些主题最近更多出现？ | 按周的趋势线或堆叠柱图 | 无记录不等于没有关注；支持绝对条数与占比区分 |
| 思考演变 | 同一个问题，我的看法怎样变化？ | 日期—观点—转折的时间线 | 不把表达差异自动当成成长或退步 |
| 跨领域关联 | 亲子、产品、AI 等思考是否有共通点？ | 关联卡片，后续可做小型关系图 | 标明这是 AI 提出的联系，不冒充原文事实 |
| 价值与张力 | 哪些目标反复拉扯，例如效率与陪伴？ | 两端观点与支持原文并列 | 不作人格判断，不把情境差异都说成矛盾 |
| 情境与感受 | 什么情境反复伴随某种自述感受？ | 情境—感受—应对的归纳卡片 | 默认不用情绪评分，不作心理诊断或因果推断 |
| 开放问题 | 哪些问题出现多次，仍未看到明确回答？ | 可回访的问题列表 | 「没记录答案」不等于现实中没解决 |
| 想法到尝试 | 哪些想法有了后续验证？ | 想法 → 尝试 → 反馈时间线 | 不把设想当成已执行的行动 |
| 产品与创作种子 | 哪些观察能形成文章、产品假设或小实验？ | 灵感卡 + 引用 + 最小验证建议 | 建议不等于用户承诺，不自动创建任务 |
| 值得回看的片段 | 哪些细节、洞见或生活瞬间值得保留？ | 原文摘录 + 简短说明 | 原话与 AI 改写明确区分 |

### 6.1 基于用户背景的示例（虚构，仅说明能力）

假设多条记录分别写到：不想过度控制孩子、产品应减少使用门槛、希望 AI 代办杂务。系统可以提出：

> 一个可能的共同关注点是「如何减少不必要的控制，让人更自主地行动」。这是否也是你对亲子关系、产品设计和 AI 工具的共同期待？

这里的价值是提出值得验证的连接，而不是断言「你是某种类型的人」。真实报告必须展示支撑该联系的不同日期原文，并保留反例或其他解释。

### 6.2 一张洞察卡片的结构

1. **发现**：一两句话，具体而非空泛赞美。
2. **依据**：日期、原文摘录、可点击来源。
3. **可能的解释**：与事实分开，使用符合证据强度的措辞。
4. **其他解释 / 材料局限**：适用时呈现，避免只找支持证据。
5. **一个追问或小实验**：可选，非说教、非任务指派。

可以提供「有启发 / 不准确」反馈，错误归类允许修改。初期不据此默默建立人格画像。

### 6.3 图表与分析的真实性

- 图表数字由程序根据记录及结构化分类计算，不能让模型凭印象编造。
- 显示时间范围、记录总数、活跃记录日数及统计口径。
- 一条记录允许多个主题；主题标签由内容涌现，背景主题只是候选，不是固定套用的类别。
- AI 标签也可能出错，允许查看每个类别的来源。
- 记录次数不等于实际投入时间、生活占比、幸福程度或心理健康状态。
- 优先可读的条形图和时间线，不为「图文」强加词云、雷达评分或复杂关系图。
- 无需首版接入图片生成模型；这里的「图」主要是有依据的信息可视化。

### 6.4 长期生成流程

- 原始记录 + 可追溯信息点是基础；日整理作为辅助，不能是长期分析的唯一输入。
- 分块提取主题、问题、观点与来源，再跨日期聚合；针对候选洞察回查原文与反例。
- 模型输出受校验的结构化结果，前端以固定组件呈现，不执行模型返回的任意 HTML / JS。
- 记录范围、来源版本、模型和提示词版本，使结果可复现地追踪。
- 手动触发、展示进度，失败可重试；生成期间可继续记随笔。
- 避免每次打开页面都重新生成，基于来源版本复用已有结果。

## 7. 数据设计建议

采用服务端持久化，按日期组织展示与查询；「按天存储」不必意味着每天一个数据库或文件。支持按日期导出 Markdown，满足长期保存与迁移。

建议实体：

- `entries`：ID、正文、记录时间、修改时间、归属本地日期、版本、删除状态。
- `daily_summaries`：日期、正文/结构化段落、来源 ID 与版本、模型、提示词版本、生成时间、状态。
- `insight_reports`：起止日期、结构化分析、图表数据、来源快照、模型、生成时间、状态。
- `generation_jobs`：任务类型、输入版本、状态、错误与重试信息。

原文和 AI 派生结果分开存储。重新生成可保留有限历史版本；原文删除后，相关整理和洞察需失效，并提供清理派生内容的策略，避免删除后仍暴露私人文字。

时间以 UTC 存储，同时依据配置的 IANA 时区确定日归属。配置时区后保持稳定，不能跟随服务器或访问设备时区悄悄变化；跨午夜生成采用明确的来源快照。

## 8. 技术与安全建议（待确认）

### 部署取向

默认按单人、自托管、一个服务实例设计。建议 TypeScript 全栈 + SQLite + 持久磁盘，以低维护成本为主，不上微服务、向量数据库或复杂用户系统。

具体框架待开发时确定；若部署环境无持久磁盘或需多实例，应改用托管数据库，不直接照搬 SQLite 单机方案。

### 密码登录

- 服务端私有配置文件保存密码哈希而非明文，提供设置 / 重置密码的本地命令。
- 密码验证后创建服务端会话，使用 HttpOnly、Secure、SameSite Cookie；写操作检查来源 / CSRF。
- 登录限速、失败退避，密码修改使旧会话失效。
- 公网部署必须 HTTPS；所有记录、导出、AI 任务接口均需鉴权。
- 不设置公开注册入口，不能因单用户而省略鉴权。

### AI 配置

服务端配置文件建议包含：`auth.passwordHash`、`app.timezone`、`llm.baseUrl`、`llm.apiKey`、`llm.model`。可选分别指定日整理与深度分析模型。

密钥不得下发浏览器或写入 Git；私有配置限制文件权限，并可支持环境变量覆盖。没有 API 密钥时依然能够记录、回看、搜索和导出，只有 AI 功能不可用。

### 隐私与可靠性

- 第一次使用 AI 时明确告知：所选范围的记录会发送给配置的大模型服务商。自托管不等于数据不出服务器。
- 亲子、家庭、心理相关记录高度私人；默认不记录正文到应用日志，不接第三方行为追踪。
- AI 无执行工具权限，将记录内容仅视作待分析资料，不执行记录中包含的指令。
- 定期备份数据库，提供 Markdown / JSON 导出，并验证恢复路径。
- 备份保留期与删除策略需说明；不能假装从主库删除就已从所有备份消失。
- 生成失败或模型不可用不影响原文读写。

## 9. 分阶段交付

### 第一阶段：把随手记录与当日整理做好

密码登录、响应式输入页、可靠保存、时间记录、按天回看、编辑删除、手动日整理、来源引用、结果过期提示、配置文件、备份和导出。

完成标准：

- 手机和桌面登录后，不选择分类就能开始写。
- 提交成功保存文字和时间；失败不丢输入；重复重试不重复入库。
- 断开 AI 配置或生成失败时，普通记录功能可正常使用。
- 不同时区/午夜边界归档正确；日期和记录时间显示一致。
- 日整理保留重要细节和粗时间顺序，可逐段回查原文；用包含数字、疑问、矛盾、回忆往事的样例人工验收。
- 更新原文后派生结果明确标记过期。
- 未登录不能读取、写入、导出记录或触发 AI；前端无 API 密钥。
- 可从备份恢复，并能导出不依赖该应用读取的原文。

### 第二阶段：做一份真正有用的月度回顾

月份 / 自定义范围选择、主题分布图、思考演变时间线、3–5 条有依据的洞察、未解问题、来源跳转、生成进度与结果复用。

完成标准：图表数字可重算，每条深度判断有来源，事实与推测分开；材料不足时明确克制。

### 第三阶段：由实际记录习惯驱动

跨月对比、专题回顾、跨领域关联、产品和文章种子、洞察反馈、对原文的自然语言检索。之后再考虑自动总结、离线同步和更丰富的可视化。

暂不做：多人协作、公开分享、注册体系、富文本编辑器、强制标签、游戏化打卡、心理评分、自动替用户执行行动。

## 10. 建议默认值与待确认事项

若没有额外偏好，建议默认：

- 单人自托管，优先支持手机浏览器，同时做好桌面横版。
- 日整理和长期分析均手动触发，避免自动上传私人记录及产生不可控费用。
- 日整理优先完整保真；月度回顾优先发现关联与变化，而非短摘要。
- 图文以统计图、时间线、证据卡为主，不生成装饰性图片。
- 无标题、无必填标签，分类全部留在回顾阶段。

开发前需确认的关键事项：部署位置及持久存储、日归属时区、准备使用的大模型服务商。其余可先按上述默认设计推进。
